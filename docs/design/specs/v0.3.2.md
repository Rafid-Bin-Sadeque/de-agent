# v0.3.2: hook false positives, DMS table mappings, fresh snapshots

Status: APPROVED 2026-11-19, BUILT 2026-11-19. Patch release: no config breaking changes, no new required keys.

Three problems found while running a real hub for a day:

1. Two guard rules blocked harmless commands.
2. The `aws` collector parses every DMS task's table mappings but keeps only a top-10-by-CDC table list, so
   "a table was added to or removed from replication" never shows in `dea diff`. Teams fall back to a hand-kept
   spreadsheet of task -> table, which drifts.
3. Snapshots go stale when nobody runs `dea snapshot` (the hub was 45 h old at session start). De-agent only warns.

## 1. Guard false positives (`scripts/secret_guard.py`)

### 1a. Heredoc bodies are not shell

Repro (blocked with "prints shell variables"):

```bash
cd hub && LIVE="$HOME/x.csv" && python3 tool.py "$LIVE" >/dev/null && python3 - "$HOME/a.csv" "$LIVE" <<'EOF'
add = sorted(set(lk) - set(sk))
EOF
```

Expected cause (confirm with a failing test first): the heredoc body is split into simple commands and a token in
the Python text is read as the bare shell builtin `set` (or another `env_dump` shape).

Fix:
- A heredoc body is only shell when the command it feeds is a shell (`bash`, `sh`, `zsh`, `dash`, `ksh`, `ssh <host>`
  with no remote command, `bash -s`, ...). For any other reader (`python3 -`, `node -`, `psql`, `cat`, ...) the body is
  data for that program: `env_dump` and the other shell-shape rules skip it.
- The body is still checked by the rule for that program: Python bodies keep going through `check_python`
  (credential-file opens, driver imports for sql_guard), SQL bodies through sql_guard. No rule gets weaker for shells.
- `echo`/`printf` of `$...PASS|SECRET|TOKEN|KEY...` is unchanged.

Tests: the repro above passes; a heredoc into `bash`/`sh -s`/`ssh host` containing a bare `set` or `printenv` is still
blocked; a Python heredoc that opens `.env` is still blocked.

### 1b. `password=` code references in hooks match lint

Repro (blocked): `python3 -c "import pymysql; kw=cfg; pymysql.connect(host=h, password=cfg['password'])"`.

Lint already exempts code references (`secretscan._CODE_REF`, 0.3.1). The hook's `PASSWORD_KV` check
(`secret_guard.py` ~:294) has no exemption.

Fix: the hook uses the same exemption. Import `_CODE_REF` (and `_PLACEHOLDER`) from `de_agent.secretscan` inside the
existing try/except, with an inline copy as fallback, so the hook still runs on system python 3.9 with no package.
Values that are code references (`cfg[...]`, `os.environ[...]`, `os.getenv(...)`) pass. A bare dotted name without
`[`/`(` (e.g. `settings.DB_PASSWORD`) stays a literal, same as lint. Literals stay blocked.

Tests: shared table of cases run against both lint `find_secret` and the hook, so they cannot drift again; the py3.9
hook suite (`DEA_HOOK_PYTHON=/usr/bin/python3`) passes.

### 1c. Self-guard gaps found while building 1a/1b (added during the build)

- **Bypass:** the plugin self-guard ("no agent may edit the plugin's own hooks, scripts, agents or skills") blocked the
  Edit tool, but a Bash `python3 - <<EOF ... open("scripts/secret_guard.py","w")` rewrite of the same file went
  through. Bash/python writes (redirects, `tee`, `sed -i`, `cp`/`mv` onto, Python `open(...,'w')`/`write_text`) to the
  protected paths must be denied the same way unless `DEA_ALLOW_PLUGIN_EDITS=1`.
- **False positive:** a Bash python rewrite of `scripts/secret_guard.py` was refused by the dbt-test-overwrite rule,
  which should only match dbt test files (`tests/**/*.sql`, schema yml `tests:`). Narrow its path match; add a test.
- **False positive:** a Bash python edit of `cli/src/de_agent/cli.py` was refused with "python can write to
  de-agent.yaml": the script merely contained that string as text. Match real write targets, not any mention.
- The self-guard's protected set includes `cli/src` and `cli/pyproject.toml` by design (hooks import those classifiers),
  so building any 0.3.x change needs a maintainer session with `DEA_ALLOW_PLUGIN_EDITS=1`. Same Bash-route gap as above:
  python rewrites of `cli/src` files were not caught either.

## 2. `dms_table_mappings` section (aws collector)

In `collectors/aws/_aws_core.py::gather_dms`, add a section `dms_table_mappings`: one row per (task, source schema,
source table) that the task's selection rules currently include.

| field | value |
|---|---|
| `task` | task identifier |
| `schema`, `table` | source schema and table |
| `target_schema`, `target_table` | after `rename` transformation rules (schema and table) |
| `rule` | `explicit`, or `wildcard <schema>.<table>` for tables matched by a `%` rule |
| `source_endpoint`, `target_endpoint` | endpoint identifiers |

Resolution:
- Explicit include rules give their table directly. Wildcard include rules are resolved from the task's table
  statistics (already fetched for `dms_top_tables`; keep the list instead of discarding it). A wildcard that matches
  nothing yields one row with `table` = the pattern and `rule` = `wildcard ... (unresolved)`.
- Exclude rules remove matching rows. DMS `%` = glob `*`, case-sensitive match.
- Column transformation rules are not in this section (they stay in `dms_tasks.rules`).
- Cap: `options.dms_mappings_max` (default 5000 rows across tasks); over the cap the section is truncated and listed in
  `meta.truncated`. Check that table statistics pagination is not capped below the task's table count by `MAX_PAGES`;
  raise the per-task page limit for this call if it is.

Registration (`collectors/aws/__init__.py`): `list_keys["dms_table_mappings"] = ["task", "schema", "table"]`; not a
ranking or windowed section, so `dea diff` lists added and removed tables; `target_*` changes show as changed rows.
No volatile fields.

Render (`render.py`, DMS block):
- A "Table mappings" line per task: `<n> tables (<k> via wildcard)`, and a pointer that the full list is in the
  snapshot JSON / `dea find`.
- Signal (info) when a diff against the previous snapshot shows mapping changes: `DMS mappings: +<a> / -<r> table(s)
  in <tasks>`. Reuse the existing diff machinery; do not duplicate key logic in render.
- Same-target duplicates: a warn signal when one target endpoint + schema + table is mapped by more than one task
  (two tasks writing one table).

Export: `dea export dms-mappings [--csv PATH]` writes the section from the latest snapshot as CSV
(columns = the fields above). Read-only, no AWS call. This lets a team regenerate its spreadsheet from the hub instead
of editing it by hand.

Tests: Stubber/moto fixtures with explicit, wildcard, exclude, rename and an unresolved wildcard; diff test showing
an added and a removed table between two snapshots; cap test; ssh path unchanged (collector stays stdlib + boto3).

## 3. Keeping snapshots fresh

No scheduler inside de-agent (a CLI should not install background jobs on its own).

- `dea schedule print [--at HH:MM] [--sources a,b]` prints a ready-to-install job for the current OS: a launchd
  plist on macOS (`~/Library/LaunchAgents/io.de-agent.snapshot.plist`), a crontab line elsewhere. The job runs
  `dea snapshot` with `DEA_HUB` set, logs to `<hub>/.dea/logs/snapshot.log` (rotated, keep 7). Prints only; the human
  installs it (`launchctl load` / `crontab -e`), and the output says so.
- The SessionStart stale-data row adds the hint `dea schedule print` when the snapshot is older than
  `hub.snapshot_max_age_hours`.
- docs: "Keep snapshots fresh" section in docs/configuration.md or START_HERE.

Tests: plist and cron output golden files; no file is written by `schedule print`.

## Build notes (deviations, 2026-11-19)

- Target names also apply `convert-lowercase`/`-uppercase` and `add-`/`remove-prefix`/`-suffix` schema/table rules, not only
  `rename` (MySQL -> Postgres/Redshift tasks commonly lowercase).
- A task whose table statistics fail to read marks `dms_table_mappings` truncated; `dea diff` then drops removals and the mapping
  signal for that section (its wildcards are unresolved, not removed).
- "Keep snapshots fresh" docs live in docs/START_HERE.md: docs/configuration.md is generated from the config models.
- 1c: the interpreter-write rule matches quoted path literals in code that also writes; from inside the plugin checkout (non-maintainer)
  a writing script that only reads a protected path is refused too. Accepted: it fails closed and only affects the plugin checkout.
- `dea export` reads the newest snapshot that ran each aws source, so a later `dea snapshot --source other` does not hide it.

## Out of scope

MySQL-side DMS checks, CloudTrail "who changed the task", Google Sheets writing (a team's Airflow job can call
`dea export` or do its own boto3 export).
