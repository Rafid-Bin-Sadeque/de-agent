# M5 spec: docs, packaging, release candidate (local), dogfood

Depends on M1–M4. Everything here is local. Pushing, publishing, the PyPI upload, the GitHub repo and the announcement are the
maintainer's own actions and are NOT done here.

## 1. Docs (written for a data engineer who has never heard of the project)

- **README.md** (≤ 250 lines):
  1. The problem, in 3 lines.
  2. What you get: 4 bullets with one concrete example each.
  3. A mermaid architecture diagram.
  4. The 60-second tour (existing).
  5. **Results**: the M4 headline table, linked to the full report.
  6. Install: the plugin marketplace plus `uv tool install de-agent` / `pipx install de-agent`, with `[aws]` as an extra.
  7. Quickstart on your own platform: `dea init` → edit `de-agent.yaml` → `dea doctor` → `dea scan` → `dea snapshot`, or use the `hub-init` skill.
  8. Supported systems table.
  9. A safety model summary linking to SAFETY.md.
  10. A command reference table.
  11. Skills and agents table.
  12. FAQ: "Why not a vector DB?", "Does it send my data anywhere?", "Can the agent write to prod?", "Cost?".
  13. Contributing and License.
- **docs/architecture.md**: the layers (collectors → platform/, scanners → catalog/, hub pages, FTS index, hooks, agents, skills), data flow
  diagrams (mermaid), and the file layout of a hub. It moves the durable parts of KNOWLEDGE_ARCHITECTURE.md into user-facing form; keep
  KNOWLEDGE_ARCHITECTURE.md as the design rationale.
- **docs/adoption.md**: day 1 (one warehouse + one Airflow), week 1 (scan repos, profiles, status), scaling to hundreds of projects
  (domains, CODEOWNERS, scheduled snapshots via cron/CI/Airflow, hub lint in CI), and team rollout (shared hub repo, per-person approve key).
- **docs/writing-a-collector.md** and **docs/writing-a-scanner.md**: the protocol, a minimal example, fixtures, golden renders, and the read-only rules.
- **docs/skills.md**: each skill with its trigger phrases, what it does, and the never-dos.
- **docs/configuration.md**: the full `de-agent.yaml` reference, generated from the pydantic models (`dea config schema` writes a JSON Schema plus a markdown table). Add that command. A test fails if the doc drifts.
- **CHANGELOG.md**: v0.1.0 (Keep a Changelog format).
- **CODE_OF_CONDUCT.md**: Contributor Covenant 2.1, by reference link plus a short summary. Update **CONTRIBUTING.md** with the dev setup, the test tiers (unit / integration / demo / perf / walkthrough / evals) and how to add a fault.
- Remove "pre-alpha", set the status to "v0.1.0". Remove `docs/PLAN.md`'s working-notes tone: keep it as `docs/design/PLAN.md` with a
  header "original design plan", and move `docs/specs/` to `docs/design/specs/`.

## 2. Packaging

- pyproject: name, version 0.1.0, description, readme, license (Apache-2.0), classifiers, `project.urls` with `OWNER` placeholders,
  `optional-dependencies.aws`, and the console script `dea`.
- Build an sdist and wheel locally (`python -m build` in cli/.venv). `twine check` must pass.
- Fresh-venv smoke: install the wheel into a new scratch venv, then run `dea --help`, `dea init` in a scratch dir, `dea doctor`, and `dea lint`.
- The wheel must include the hub templates and the vendored hook dependencies it needs. Test that by installing the wheel and checking `dea guard-test`.
- plugin.json and marketplace.json are at version 0.1.0. `claude plugin validate . --strict` passes.
- Name check, read-only web lookups only: is `de-agent` free on PyPI, and is `github.com/<any>/de-agent` common? Report and
  suggest 2 alternatives if it's taken. Do not register anything.

## 3. Release candidate (local only)

- Create an orphan branch `release/v0.1.0` whose single commit is the final tree of main. Message: `de-agent v0.1.0` plus the trailer.
- Run the deny-list grep (`DEA_DENYLIST_FILE`) over **that branch's full history** (`git log -p`), and over all file contents at that commit. Both must be clean.
- Tag `v0.1.0` on that commit (lightweight, local). main keeps its full local history untouched.
- Write `RELEASE_CHECKLIST.md` (in the repo) with the maintainer's exact steps:
  1. Create the GitHub repo.
  2. `git push <remote> release/v0.1.0:main --tags`.
  3. Replace the `OWNER` placeholders.
  4. Upload to PyPI (`twine upload`) after a TestPyPI dry run.
  5. Enable the CI secrets for evals.
  6. Record the demo GIF (vhs/asciinema command given).
  7. Announce.

## 4. Dogfood on a private platform (outside the repo, read-only)

- Build a NEW hub folder outside this repo, next to (never inside or over) the maintainer's existing hand-written hub.
- Configure scans of a private Airflow and SQL repos, and read-only sources (one Postgres warehouse, AWS via `exec: ssh:<host>`).
  Leave out any source the maintainer has flagged as fragile.
- Run doctor, scan, snapshot, lint, and three real find/edges/impact lookups. Port the hand-written pages as drafts.
- Write a MIGRATION.md in that folder: timings, what the generated pages replace, what still needs a human, lint findings, bugs found,
  and the switch-over steps for the maintainer, which are NOT executed.
- Fix bugs generically in the repo with fictional fixtures, as `M5.1: dogfood fixes`, then rebuild the release branch.
- The concrete paths, hosts and sources are given privately to the executor and never written into this repo.
- If a permission check blocks a live part, skip it and record it in MIGRATION.md.

## 5. Launch draft (outside the repo)

`LAUNCH.md` in the dogfood hub folder holds:
- a LinkedIn post draft (≤ 1,300 characters, first person, how a data team adopts AI without slop: generated ground truth, enforced
  guardrails, measured evals, with the M4 numbers)
- a 5-line repo description
- 3 screenshot/GIF ideas

It contains no company data beyond what the maintainer chooses to add.
