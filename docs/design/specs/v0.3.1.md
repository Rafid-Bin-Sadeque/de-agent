# v0.3.1: one hub for every session (multi-repo fixes)

Status: approved 2026-11-10. Scope: bug fixes found when one hub serves Claude sessions opened in many
different repo folders (`DEA_HUB` set, plugin installed at user scope). No new collectors, no CLI changes
beyond what is listed. Hooks stay stdlib-only and Python 3.9 compatible.

## §1 Guards resolve the hub, not the session folder

Problem: `sql_guard.guard_mode`, `sql_guard.approved_hashes` and `cli_guard.read_config` read
`de-agent.yaml` from `CLAUDE_PROJECT_DIR`/`cwd`. A session opened in a repo (no `de-agent.yaml` there)
silently falls back to `strict` and to no approved plans, even when the hub says `mode: ask`.
`query_log.py` has the same project-dir lookup.

Fix:
1. Add `find_hub(cwd)` to `scripts/_guardlib.py`, mirroring `cli/src/de_agent/hubpath.py` exactly:
   `$DEA_HUB` (expanded; must be a dir) → nearest `de-agent.yaml` walking up from `cwd` →
   `~/.config/de-agent/config.yaml` `hub:` (absolute existing dir). Returns `None` when nothing matches.
2. `scripts/session_context.py:find_hub` becomes a thin call to the `_guardlib` one (keep the name;
   `stop_check.py` imports it from `session_context`).
3. `sql_guard` (mode + approved plan hashes), `cli_guard` (mode + `cli_allow`) and `query_log` use
   `find_hub(project_dir) or project_dir`. No hub at all → unchanged behaviour (`strict`, no allow list).
4. Do NOT change path-based guards (`secret_guard`, `self_guard`, `test_guard`): they reason about files
   relative to the session folder.
5. Tests (pytest + the py3.9 hook suite): session folder without `de-agent.yaml` + `DEA_HUB` → hub with
   `mode: ask` gives `ask`; same without `DEA_HUB` gives `strict`; an approved plan stored in the hub is
   honoured from another folder; `cli_allow` from the hub applies; walk-up from a nested folder finds the hub.
   Existing red-team cases must still pass.

## §2 Configurable map file, optional session injection

Problem: a hub that already keeps its map under another name (and already loads it through a CLAUDE.md
import) gets `map.md is missing` lint errors, and renaming would inject the map twice per session.

Fix:
1. `HubConfig` gains `map_file: str = "map.md"` (relative path inside the hub, no `..`, must end `.md`)
   and `session_map: bool = True` (field descriptions + `docs/configuration.md` + config doc generator).
2. `session_context.build`: read `map_file` / `session_map` from `de-agent.yaml` with stdlib regex
   (same style as `max_age_hours`); when `session_map` is false, skip the map but keep due rows,
   stale-platform rows and the footer.
3. `lint.py`: map-budget and the orphan-project index use `map_file`; `find.py` page-kind classification
   treats `map_file` as `"map"`.
4. Tests for both defaults and the override.

## §3 status.md: more date formats

Problem: due dates only count in tables whose header has `Due`/`Date` + `State`/`Status`, and the date
cell must be a bare `YYYY-MM-DD`. Common hand-written forms are missed.

Fix (one shared parse rule for `session_context.due_rows` and `lint.status_rows`):
1. Header synonyms: date column `due|date|when`; state column `state|status`.
2. Date cell: strip markdown emphasis (`**`, `__`, `*`, `_`, `~~`) and a leading `~`, then take a leading
   `YYYY-MM-DD`; trailing text (`(overdue)`, `morning`) is allowed. No leading date → row ignored.
3. Bullet items: under a heading (any level) whose text matches `dated|due|deadline` (case-insensitive),
   a list item (`- ` / `* ` / `1. `) whose text, after optional emphasis markers, starts with
   `YYYY-MM-DD` is a due row. Done when the whole item is struck through (`~~…~~` wrapping the text) or
   it is a checked task (`- [x]`). Bullets under other headings (e.g. "Done") are never due rows.
   For lint, `cells` = `[first 100 chars of the item text]`, `state` = `"done"`/`""`.
4. Horizon and overdue logic unchanged. Tests for every form above, including a "Done" section that must
   be ignored.

## §4 Lint false positives

1. Topic pages: only direct children of `projects/` are profiles. Pages in `projects/<name>/` are topic
   pages of that profile: exempt from `profile-frontmatter` and `orphan-project` (still page-budget,
   broken-link and secret checks).
2. `secret-in-hub` / `secretscan.PASSWORD_KV`: a value that is a code reference is not a secret —
   `IDENT[...]`, `IDENT(...)`, `IDENT.IDENT[...]`/`(...)`, `os.environ…`, `os.getenv(…)` (regex: value
   starts with `[A-Za-z_][\w.]*\s*[\[(]`). Dotted bare words (`a.b`) still count as secrets. Mirror the same
   exception in `scripts/secret_guard.py` only if it uses the same `password=` pattern for content scans.
   Tests: `password=MYSQL_PROD["password"]` clean; `password=hunter2` and `password=a.b` flagged.
3. Profile header (`scanners/headers.py`): cross-project edges whose only shared table is in
   `edges.ignore_tables` are omitted from the generated "cross-project edges" list (same set `dea impact`
   skips). Test with an ignored and a non-ignored table.

## §6 DAG → routine edges from config constants

Problem: DAGs that schedule routines from a config module produce no `calls` edge, so live routine pages say
"called by: none". Typical shape:

```python
# dags/marts/sales/mart_config.py
MART_PROCEDURES = [
    {"target_table": "daily_sales", "proc": "mart_sales.load_daily_sales"},
    {"target_table": "weekly_sales", "proc": "mart_sales.load_weekly_sales", "after": ["daily_sales"]},
]
# dags/sales_marts_dag.py
from marts.sales.mart_config import MART_PROCEDURES
for m in MART_PROCEDURES:
    PythonOperator(task_id=m["target_table"], python_callable=run_proc, op_kwargs={"proc": m["proc"]})
```

Fix (airflow scanner, static only, never imports user code):
1. For each DAG file, follow `from <module> import <NAME>` (and `import <module>` + `<module>.<NAME>`) where
   `<module>` resolves to a file inside the scanned repo (dag folders, their packages, or `util_packages`).
2. If `<NAME>` is a module-level literal (list/tuple of dicts, or dict of dicts), collect string values under keys
   `proc`, `procedure`, `sp`, `stored_procedure`, `routine`, `function` (case-insensitive). Accept
   `schema.name`, `schema.name(...)` and `CALL schema.name(...)`; normalise to `schema.name`, lower case.
3. Emit a `calls` edge DAG → routine for each, marked as config-derived (e.g. `via: config:<module>.<NAME>`),
   resolved against live routines exactly like existing CALL edges (unresolved stays unresolved, not dropped).
4. Only literals: names built by f-strings/concatenation are skipped (counted as dynamic). Cap: 2,000 entries per
   constant; a module that fails to parse is skipped with a warning, never a crash.
5. Tests: the shape above (both DAGs see their procs), dict-of-dicts, `CALL x.y()` form, an f-string value
   (skipped), a constant imported but unused by any DAG (no edge), a config module outside the repo (ignored).
   The routine page's "Called by" lists the DAG.
