# v0.3 spec: routines — procedures, functions and views from every SQL engine

Today de-agent knows a warehouse's tables but not the code that lives inside it. Procedures,
functions and views are where a lot of business logic sits, and the only way to see them is a
live query against the catalog. This release snapshots that code from every SQL engine we
collect from, parses it into the same edge graph the repo scanners build, and makes it
diffable and searchable. The question "which procedures read `shop.orders`, which DAG calls
them, and what changed in them since last week?" becomes one offline `dea impact` /
`dea find` / `dea diff` away. Everything stays read-only: catalog SELECTs and SHOWs only.

A bug fix ships first as 0.2.5 (§0); the routines work is 0.3.0.

## 0. Fix first (0.2.5)

- `scanners/pyexpr.py`: `iter_values` falls back to `iter_rows` when `_iter_values` returns
  None, and `iter_rows`' `range(...)` branch calls `iter_values`. For
  `for x in range(<non-constant args>)` the two recurse until `RecursionError` and `dea scan`
  crashes for the whole repo. Break the cycle: the `range` branch evaluates its arguments with
  `_iter_values` (no fallback) and yields nothing when they are not constant.
- Defence in depth: `scan_python_file` catches `RecursionError` per file, records it in the
  scan's `errors` (`file`, `reason`), and continues.
- Regression tests: the minimal `range(len(xs))`, `range(n, m)` and nested-loop cases, plus a
  corpus file with 40 such loops; `dea scan` on it must finish and report 0 errors.
- Release 0.2.5 (CLI change, so PyPI as well).

## 1. The `routines` section

### 1.1 Row contract (every engine)

One row per routine. Key: `[schema, name, args]` (args keeps overloads apart).

| column | meaning |
|---|---|
| `schema`, `name` | qualified identity (database prefix included where the engine has one, e.g. Snowflake `db.schema`) |
| `kind` | `procedure` \| `function` \| `view` \| `materialized_view` \| `trigger` |
| `args` | normalized signature, `''` for views (`(integer, text)`, types only, lower-case) |
| `language` | `sql`, `plpgsql`, `python`, `javascript`, `tsql`, ... as the engine reports it |
| `returns` | return type or `''` |
| `owner` | owning role/user where exposed, else `''` |
| `body_hash` | sha256 of the normalized body (see 1.3) |
| `body_bytes` | size of the original body |
| `truncated` | true when the body exceeded `routines_max_bytes` |
| `reads`, `writes`, `calls` | filled after parsing (§2); empty lists for non-SQL languages |
| `parse` | `full` \| `heuristic` \| `none` |

`body_hash` is NOT volatile, so a changed body is a "changed" row in `dea diff`. `owner` is
volatile (ownership churn is noise).

### 1.2 Bodies live outside the snapshot

Snapshot JSON keeps only the hash. Bodies go to a content-addressed store
`<hub>/.dea/routines/<hash[:2]>/<hash>.sql`, written once and shared across snapshots and
sources. `_prune` deletes store files no retained snapshot references. Snapshot size then
grows with the number of routines, not their text, and an unchanged warehouse costs ~0 bytes
per snapshot.

### 1.3 Normalization and redaction

- Normalize before hashing: CRLF → LF, strip trailing whitespace per line, strip a leading and
  trailing blank block. Do NOT strip comments or reformat, so the stored text is what the
  engine returned.
- Redact before writing anything (store, render, find): run the existing secret guard
  patterns (passwords in connection strings, `password=`, AWS keys, tokens) and the
  `DEA_DENYLIST_FILE` entries over every body; replace matches with `<redacted>`. Hash the
  redacted text. A `redacted: true` column marks rows where something was removed.
- Bodies over `routines_max_bytes` (default 512 KB) are cut, `truncated: true`, and the cut
  text is still hashed and stored.

### 1.4 Options (every SQL source)

```yaml
sources:
  - name: warehouse
    type: postgres
    options:
      routines: true            # default true; false skips the section entirely
      routine_kinds: [procedure, function, view, materialized_view, trigger]
      schemas: [analytics, ops] # existing filter, applied to routines too
      routines_max: 5000        # rows; over this the section errors (no silent cut)
      routines_max_bytes: 524288
```

System and extension-owned objects are always excluded (Postgres: `pg_catalog`,
`information_schema`, `pg_toast*`, and objects with a `pg_depend` `deptype = 'e'` row;
equivalents per engine below).

## 2. Engines

Every query is one statement and must classify as `read` (new cases in
`data/sql_cases.yaml`, one per query below). `sp_helptext` and other EXEC-based helpers are
never used.

### 2.1 Postgres (hand-written collector)

- Procedures + functions: `pg_proc` ⋈ `pg_namespace` ⋈ `pg_language`, `prokind in ('p','f')`
  (skip aggregates and window functions), body via `pg_get_functiondef(p.oid)` for
  `sql`/`plpgsql` and other text languages; `internal`/`c` get `language` and an empty body.
- Views: `pg_views.definition`; materialized views: `pg_matviews.definition`.
- Triggers: `pg_trigger` (non-internal) joined to the trigger function; `kind: trigger`,
  `name` = trigger name, body = `pg_get_triggerdef` + a `calls` entry to the function.
- One UNION ALL query; runs inside the existing `wrap_readonly` + lock timeout. Validated live
  against PG 12/16/17 (docker integration tests).

### 2.2 Redshift (hand-written collector)

- Procedures: `pg_proc_info` (`prokind = 'p'`) ⋈ `pg_namespace`, body from `prosrc`; header
  rebuilt from name + `proargnames` / types. Where `prosrc` is empty, fall back per
  procedure to `SHOW PROCEDURE schema.name(argtypes)` (a SHOW, classified read).
- UDFs: `pg_proc` with SQL / Python / Lambda languages.
- Views, late-binding views: `pg_views.definition` (LBVs report `with no schema binding`).
  Materialized views: `SVV_MV_INFO` for the list plus `pg_views` / `pg_get_viewdef` for the
  text; which one carries the body must be confirmed in the live check (§7), with a
  documented fallback to name-only rows (`parse: none`).
- Catalog tables only (leader-node). Never join a leader-node catalog to a compute-node
  system table in one statement (the M3.2 bug).
- The section is registered in `heavy_sections` with its own TTL option
  `routines_ttl_h` (default 24), so a light snapshot reuses the prior routines unless the TTL
  ran out or `--deep` is passed. Fixture-tested; live check is manual and light (§7).

### 2.3 Packs (declarative, no code per engine)

Packs get a reserved section name `routines`. `check_pack` enforces the row contract (1.1
columns present; `key` must be `[schema, name, args]`), the section may set `limit` up to
`routines_max` (overriding the 1000 cap for this section only), and must return a
`definition` column. `PackCollector.collect` then does 1.2–1.3 generically: hash, redact,
store, drop `definition` from the row, record `body_hash`. New sections:

| pack | procedures / functions | views | triggers |
|---|---|---|---|
| `mysql` | `information_schema.routines.routine_definition` (NULL without `SHOW_ROUTINE` → row kept, `parse: none`, signal info "grant SHOW_ROUTINE for bodies") | `information_schema.views.view_definition` | `information_schema.triggers.action_statement` |
| `snowflake` | `information_schema.procedures.procedure_definition`, `information_schema.functions.function_definition` (per database param) | `information_schema.views.view_definition` | — |
| `mssql` | `sys.sql_modules.definition` ⋈ `sys.objects` (`P`, `FN`, `IF`, `TF`) | same, type `V` | same, type `TR` |
| `bigquery` | `region-<r>.INFORMATION_SCHEMA.ROUTINES.routine_definition` | `INFORMATION_SCHEMA.VIEWS.view_definition` | — |
| `databricks-system` | `system.information_schema.routines.routine_definition` | `system.information_schema.views.view_definition` | — |

`postgres-lite` gets the same section (same SQL as 2.1) so pack-only users have it too. Each
pack keeps its `validated:` honesty: mysql + postgres-lite live (docker); the rest fixtures.

## 3. Edges: routines join the graph

### 3.1 Parsing

New `scanners/routines.py`, called from `run_scan` next to `_aws_edges`, over the latest
platform results of every SQL source:

- Load each body from the store, parse with `analyze_sql(body, dialect)`. Procedural bodies
  (`plpgsql`, Redshift procedures, T-SQL) reuse `scanners/sql.py`'s body-flow path; anything
  parsed by regex is `heuristic`, as today.
- Non-SQL languages: no parsing, node only.
- Results are written back into the catalog (not the snapshot): `catalog/routines.json`
  `{source: {qualified_name+args: {kind, reads, writes, calls, parse}}}`, cached by
  `body_hash` so an unchanged routine is never re-parsed.

### 3.2 Nodes and edges

- Routine owners in `edges["tables"][t].readers/writers` use ids
  `proc:<source>:<schema.name>`, `function:<source>:...`, `view:<source>:...`,
  `via: "routine"`, `file: "<source>:<schema.name>"`.
- New top-level `edges["calls"]`: `{from, to, via, file}` for every DAG→routine,
  routine→routine and trigger→function call. Today a DAG's `CALL` only becomes DAG→table
  edges through the procedure body and the procedure itself is invisible; now the procedure is
  a node on the path.
- `_proc_index` merges repo-scanned and live routines. Resolution order for a `CALL x.y` in a
  DAG: (1) a configured connection→source mapping, (2) a unique live match, (3) a unique repo
  match, (4) `unresolved` listing all candidates. New scan option:

```yaml
scans:
  - name: pipelines
    type: airflow
    path: ../pipelines
    connections: {warehouse_conn: warehouse}   # Airflow conn_id → de-agent source
```

### 3.3 Repo vs live drift

When a routine exists both in a repo `.sql` scan and live, compare normalized hashes. A
mismatch is a warn signal on the live source: `routine analytics.refresh_orders differs from
sql/procs/refresh_orders.sql:12 (live changed outside the repo, or the repo is ahead)`. This
gives teams without a migration gate (Flyway, Liquibase, sqitch) a cheap way to notice
out-of-band procedure edits.

### 3.4 Impact

- `dea impact <table>` walks table → reading routines → tables they write → ..., and lists
  the DAGs that call each routine on the way.
- `dea impact proc:<schema.name>` (or `function:` / `view:`) is new: what it reads, what it
  writes, who calls it, and everything downstream.

## 4. Render, find, diff

- `platform/<source>.md` gets a Routines summary: counts per schema × kind, parse coverage
  (`full / heuristic / none`), truncated and redacted counts, and changed routines since the
  previous snapshot.
- One page per routine: `platform/<source>/routines/<schema>.<name>.md` with header
  (kind, language, args, owner, hash), reads/writes/calls as links, callers (DAGs), and the
  redacted body in a fenced block. `dea find` picks these up with no change to the index;
  `split_ident` already makes `schema.name` searchable by parts.
- `dea diff`: added / removed / changed come for free from `list_keys`. For changed rows with
  a `body_hash`, the diff renderer loads both bodies from the store and prints a unified diff
  (cap 80 lines per routine, then `... N more lines`). Renamed routines show as removed +
  added.

## 5. Docs

- `docs/routines.md`: what is collected per engine, the privileges each needs (Postgres: none
  beyond `CONNECT` + `USAGE`; MySQL `SHOW_ROUTINE`; Snowflake `USAGE` on the schemas; SQL
  Server `VIEW DEFINITION`; BigQuery `bigquery.routines.get`), redaction, the store, the TTL.
- `docs/read-only-access.md`: add the routine privileges to each engine's read-only login.
- README "What it knows" and START_HERE: one line each. CHANGELOG 0.3.0.
- **Never-dos:** never call EXEC/CALL to read a definition; never store an unredacted body;
  never parse non-SQL bodies as SQL.
