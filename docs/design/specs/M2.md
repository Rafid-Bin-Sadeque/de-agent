Depends on M1a–M1c. This milestone turns the CLI and hub into something an engineer actually talks to: "dbt_build is failing",
"is extract_shop healthy?", "onboard this repo". Zero company data, and every example uses the Acme demo.

runs against the demo. Not approved: push, publish, global installs, non-local hosts.

## 1. New CLI commands

**`dea query <source> "<sql>" [--format table|json|csv] [--limit 200]`**
- Runs one statement on a configured source.
- Uses the source's `conn` and secret ref from de_agent.yaml, so agents never handle connection strings.
- The statement is classified first with `sqlclass`, and any write gets exit 2 and a message.
- It is then run inside the existing `wrap_readonly` (`BEGIN READ ONLY`, statement_timeout, lock_timeout).
- Output is capped at `--limit` rows, with "N more rows" noted.
- This becomes the default way the runner reads. Raw `psql` still works and stays guarded by the hooks.

**Plan files** live in `.dea/plans/<id>.md`:
```markdown
---
id: 2026-10-27-fault01-schema-drift      # slug, unique
title: Restore extract_shop after source column rename
risk: low | medium | high
sources: [warehouse]
statement_timeout: 300s
---
## Why            (root cause + evidence lines, cited from snapshot/diff/query output)
## Steps
### 1. <title>
```sql source=warehouse
ALTER TABLE ...;
```
```sql verify source=warehouse expect="= 0"
SELECT count(*) FROM ...;
```
### 2. ...      (a step may set `transaction: false` on its fence for VACUUM / CREATE INDEX CONCURRENTLY)
## Rollback
```sql source=warehouse
...
```
## Not doing     (unsafe alternatives considered and rejected, with why)
```
`verify` blocks must classify as reads. A block with no `source=` is an error.

**`dea plan check <id>`**
- Parses the file and classifies every statement, reporting kind, write/read and the destructive flag (DROP/TRUNCATE/DELETE without WHERE).
- Lists the sources and prints each statement's hash (the same normalisation as `sql_guard`).
- Errors on:
  - a read-only verify that classifies as a write
  - an unknown source
  - a destructive statement in a plan marked `risk: low`
- Exit 1 on any error.

**`dea approve <id>`**
This is a human-only action and is enforced in three layers:
1. It requires an interactive TTY. It prints the full plan check and asks the human to type the plan id. There is no `--yes` flag and no env override.
2. It writes `.dea/plans/<id>.approved` with the statement hashes, an approver (`git config user.email` or `$USER`), a timestamp and an
   **HMAC-SHA256** over all of that.
   - The key lives in `~/.config/de-agent/approve.key`, created 0600 on first use.
   - The guard and `dea apply` reject an `.approved` file with a bad MAC.
3. Hooks deny every Claude tool path to approval, for every agent including the main session:
   - Bash commands containing `dea approve`, `approve.key` or `.approved`.
   - Write/Edit/NotebookEdit on `**/.dea/plans/*.approved`.
   - Read of `approve.key` (secret_guard).

   The deny message tells the human to run `dea approve <id>` in their own terminal.
4. Threat model, documented in `docs/SAFETY.md`: this stops accidents and casual bypass. It is not a sandbox against a hostile local process. Say so plainly.

**`dea apply <id> [--rollback] [--dry-run]`**
- Verifies the MAC and re-hashes every statement in the plan. Any statement not in the approved set aborts before anything runs.
- Runs the steps in order, one transaction per step unless `transaction: false`, with the plan's statement_timeout.
- After each step it runs that step's verify blocks and evaluates `expect`. On a failed verify or statement error it stops and runs no further steps.
- Writes `.dea/plans/<id>.applied.json` per step: status, rowcount, duration, verify results and error.
- `--rollback` runs the Rollback section (its hashes must also be approved).
- `--dry-run` prints what would run.
- Hook rule: Bash `dea apply` is allowed only when `agent_type == "de-agent:executor"`. Everywhere else it is denied, with "hand the plan to the executor agent".

**`dea plans`** lists the plans with their state: draft / checked / approved / applied / failed / rolled back.

## 2. Agents (`agents/*.md`, model aliases only)

| agent | model | tools | role |
|---|---|---|---|
| `runner` | sonnet | Bash, Read, Grep, Glob | Read-only lookups: `dea query/find/edges/impact/snapshot/diff`, log tails. Returns compact answers with the command used. Never edits. |
| `explorer` | sonnet | Read, Grep, Glob, Bash | Repo questions. Order: `dea find` → catalog/edges → code. Returns conclusions with file:line, never file dumps. |
| `executor` | sonnet | all | Runs an approved plan: `dea plan check` → `dea apply` → post-apply `dea snapshot` + `dea diff`. Also makes code edits named in the plan. Stops and reports on anything the plan doesn't cover. Never edits a plan file. |

The main session plans and decides; there is no planner agent. Each agent prompt is ≤ 80 lines. Guard behaviour lives in plugin hooks keyed
on `agent_type`, never in agent frontmatter (plugin agents ignore their own hooks and permissionMode).

## 3. Skills (`skills/<name>/SKILL.md`, plus `references/` where needed)

Every skill states, in order: when to use it, inputs, steps (which agent does what), the output format, and the never-dos.

| skill | what it does |
|---|---|
| `hub-init` | New hub. Asks for the folder of repos and the sources, drafts `de-agent.yaml` (secret refs only, never values), then `dea init` → `dea doctor` → `dea scan` → `dea snapshot`, and drafts `map.md` from the results. Ends with a lint-clean hub. |
| `onboard-project` | Adds one repo: scan config, a profile page (asks the human 3–5 questions for the body: purpose, owners, gotchas), rescan, and a proposed integration page for each new cross-project edge. |
| `hub-sync` | End of session. Builds a proposal from `dea diff`, plans applied, and git changes in scanned repos since the last sync: status.md rows (done/in-progress/dated checks), profile body edits, integration pages. Shows it as one diff for the human to accept. Never touches generated blocks or catalog/platform. |
| `pipeline-check` | Takes a "DAG / table / model" name. Gathers the catalog line, edges, snapshot sections (runs, failures, freshness, tests) and `dea diff`, then gives a verdict: healthy / degraded / broken, with evidence lines. |
| `incident-triage` | Takes a symptom in plain words and works through: (1) fresh snapshot + diff, (2) ranked hypotheses from signals and edges (upstream first), (3) runner checks for each, cheapest first, (4) root cause with cited evidence, (5) the safe fix as a plan draft via `plan`, (6) the unsafe fixes it rejected, in "Not doing". |
| `plan` | Writes `.dea/plans/<id>.md` from the triage or the request, runs `dea plan check`, then tells the human the exact `dea approve <id>` command to run in their terminal. After approval it hands off to `executor` and reports the applied result plus the post-apply diff. |
| `audit` | Postgres pack in `references/postgres.md`: R1 workload (pg_stat_statements if present, else pg_stat_activity samples), R2 tables (bloat, dead tuples, seq-scan-heavy, unused indexes), R3 locks/connections/long transactions, R4 settings vs size. The runner runs the sections in parallel and the main session applies the pack's verdict rules (bottleneck layer first, hardware last). Writes `audits/<source>-<date>.md` with a then-vs-now table against the previous audit. |

Deferred to M2b (spec later): `backfill`, `schema-change`, `new-pipeline`.

## 4. Hooks added

- **Approval and apply guards**, as in §1.
- **`stop_check` (Stop hook):** if any `.dea/plans/*.applied.json` is newer than the latest snapshot, block the stop once with "re-run `dea snapshot`
  and confirm the fix in `dea diff`". It keeps a marker per plan so it never loops. Otherwise, if files under a scanned repo changed this
  session, add a one-line non-blocking suggestion to run `hub-sync`.
- Every new hook script keeps the stdlib + vendored sqlglot rule and passes under `/usr/bin/python3` (3.9).

## 5. Tests

- **Unit:**
  - plan parser (fences, verify, transaction flag, rollback)
  - `plan check` errors
  - hash parity with sql_guard
  - MAC create/verify/tamper (edited statement, edited hash list, swapped key)
  - `apply` ordering, stop-on-failure, verify expect parsing (`= 0`, `> 0`, `between a and b`, `is null`)
  - `query` write refusal and row cap
  - `approve` refuses without a TTY (tested via `pty`)
- **Hook corpus additions**, each with an expected allow/deny:
  - `dea approve` from the main session and from the executor
  - `echo {} > .dea/plans/x.approved`
  - Write to an `.approved` file
  - `cat ~/.config/de-agent/approve.key`
  - `dea apply` from runner / main / executor
- **Demo walkthrough** (`@pytest.mark.walkthrough`, needs `DEA_DEMO=1` plus a `claude` CLI; run locally, not in CI). The scripted flow on fault 01:
  1. Inject.
  2. `claude -p --plugin-dir . "extract_shop is failing, find out why"` in the demo hub. Assert the answer names the renamed column and cites a diff/log line.
  3. `claude -p` asks for a plan, and a plan file exists that passes `dea plan check`.
  4. The test approves through `pty` (the human step).
  5. `claude -p` asks the executor to apply. `applied.json` reports all steps ok.
  6. `dea snapshot` + `dea diff` show the failure signal gone.
  7. Assert no guard denial was bypassed (query_log has no write outside the plan).
  8. Record the transcript summary in `demo/faults/01_schema_drift/WALKTHROUGH.md`.
- `claude plugin validate . --strict` with the agents and skills present.
